# AgentScape 目标与实施路径重规划

> 2026-11-13 用户方向修订：优先支持 AI 自由编写完整 Three.js 项目、动态扩展世界能力，框架保证按需接入。下文原“先收敛有限标准任务”的阶段顺序保留为讨论记录；新代码项目契约与实现入口见 [Code Project](../docs/modules/code-project.md)。不以固定动作清单限制创作。

日期：2026-11-12。性质：基于当前仓库的产品方向与实施建议；不改变公共契约，不自动修改既有任务状态，也不表示后续实现或发布已经完成。

## 1. 项目的目标

**把用户对三维世界的描述，变成一个人和 AI 都能操作、系统能够验证行为结果、能够保存和继续使用的交互式世界。**

长期定位是面向智能体的世界编译器与运行时。近期交付形态是可接入 AI 工具的浏览器 3D 世界创作与运行工具。

第一批服务对象建议收敛为：希望用 AI 创建交互场景、接入自己的 Agent、调试空间任务的开发者和技术创作者。先证明这类用户能独立完成工作，再扩展到大众创作。

用户应当能够：

1. 描述一个小场景，或打开已有项目。
2. 得到满足明确能力要求的物体、布局和交互。
3. 手动操作场景，或让 AI 观察、规划和执行任务。
4. 看清哪些对象只是展示、哪些参与物理、哪些具有可执行交互，以及本次操作是否实际通过验证。
5. 保存作品，在干净环境重开，重新操作并取得新的验证证据。

项目价值在于上述过程能够连起来。视觉表现、代码资产、生成服务、编辑器和 MCP 都围绕这个过程安排优先级。

## 3. 当前规划为什么需要调整

- 工作横跨 Runtime、生成、资产、Studio、SDK、MCP、原生项目接入与大型世界，缺少一个约束排期的用户交付物。
- 文档同时出现 v2、v2.1、v2.2 和不同包名；`docs/status.md` 主要描述文档结构，不能直接回答当前产品走到了哪一步。
- 本次聚合任务库共 1181 条：DONE 258、READY 878、DISCOVERY 29、BLOCKED 14、IN_PROGRESS 1、DEFERRED 1。按现有依赖计算有 674 条可执行任务；这是工程候选库，不能直接作为本轮排期。
- `V2-PR-09` 仍为 IN_PROGRESS；独立首次使用文件仍为 not performed。候选提交的托管 CI 本次未查询，不能据此断言其当前通过或失败。
- 视觉可见、资产准入、动作执行与任务验证是不同层次。产品需要向用户解释这些差别，避免扩大宣传范围。

## 4. 唯一近期验收场景

用户描述：“创建一个小工作间，有桌子、带门的柜子和柜内杯子；让智能体开柜，取杯，放到桌上，然后保存，重新打开再执行。”

第一轮使用内置或已验证的程序化资产。随后再以真实外部资产替换其中一个物体，检验扩展能力。

验收必须同时覆盖：

- 创建：世界结构与物体能力满足意图；缺能力时明确拒绝或说明降级。
- 人工操作：用户能够选择、检查、移动物体并理解状态。
- Agent 操作：通过正式观察与动作接口完成任务，使用真实 Runtime 判定结果。
- 失败处理：缺目标、路径阻挡、目标歧义、执行取消均有确定终止与解释；不得虚报成功。
- 保存重开：保留必要资产、关系和规则；重开后重新验证，历史证据不能充当新结果。

模型未配置时仍应支持手动创作与明确标注的脚本任务验证；真实模型的质量另设评测记录。

## 5. 技术路径

```text
用户描述 / 已有作品
        ↓
意图与能力要求 → 现有 World IR（规划、规则、验收）
        ↓
内置资产 / Recipe / Three.js 代码 / GLB / 外部生成产物
        ↓
资产编译与能力准入 → 世界布局与构建
        ↓
SceneFacade → WorldRuntime
                  ↑
           Studio / SDK / MCP
                  ↓
      观察 → 执行 → 验证 → 有界恢复
                  ↓
          作品包 → 重开 → 重新验证
```

World IR 负责意图与世界构建；Scene Project/Package 负责项目描述和迁移；Runtime 持有实际状态。先定义三者已有字段的映射与边界，不强行合并格式，也不新建平行世界状态。

原生 Three.js 项目通过 attach 接入同一能力边界，宿主继续拥有 renderer、camera 和原始资源。仅显式注册的碰撞、导航与实体获得相应能力；自动发现 Scene 不等于自动理解全部世界。

## 6. 按验收门推进的路线

阶段顺序表达依赖，不是工期承诺。每阶段结束先检验交付物，再开启下一阶段。

| 阶段 | 交付结果 | 主要所有者 | 通过门槛 |
| --- | --- | --- | --- |
| M0：收敛基线 | 一份候选版本能力矩阵、统一安装与版本说明、当前迭代短队列 | planning、SDK、Studio，各模块维护自己的契约 | 明确标准任务支持世界；对齐真实包名；保留并盘点已有未提交变更；相关自动化证据绑定候选提交 |
| M1：做成最小产品 | 在一个明确支持的环境完成创建、人工操作、Agent 任务、取消、保存和重开 | application、world、Studio、SDK/MCP | 正常任务与故障用例通过；首次使用由独立参与者完成；未满足发布条件时维持开发版 |
| M2：从一句话创建小世界 | 有界自然语言输入转现有 IR，完成内置/程序化资产组合；加入一条条件规则 | application、agent、asset、world | 对固定输入集记录意图满足情况；不可实现要求明确报告；规则在重开后仍有效 |
| M3：接入真实外部资产与既有项目 | 一个外部 GLB 替换任务物体；一个原生项目完成显式物理/导航注册 | asset、generation、native-scene 接入 | 外部资产经过准入并实际完成任务；原生宿主渲染与资源所有权保持；持久化支持范围明示 |
| M4：形成可扩展平台 | 在已有闭环上增加模板、局部修复和更大可交互区域 | world、application、Studio | 增加内容后重跑任务基准；记录目标硬件的加载、帧时间、内存与释放情况，再决定优化和扩容 |

真实模型评测应在 M1 固定任务与终止语义后开展；优先沿用 `planning/product-follow-up.md` 的 12 类用例。真实生成在 M3 接入。两者分别记录服务、配置、用量与失败，不以模拟工具结果代替；实际在线调用遵守已有授权边界。

## 7. 下一轮实施顺序

1. **整理当前候选基线。** 盘点已有未提交内容；核对标准任务的世界白名单、v2.2 目录与测试夹具差异。现有 CabinetCupTask 白名单不能直接扩展成所有世界均支持。
2. **修正文档入口。** README 说明长期目标、近期产品、唯一推荐首次使用路径和能力边界；各版本文档标注历史记录与当前依据；对齐 `agentscape3d` 包名及开发/候选版本。
3. **复跑一个完整用户旅程。** 从干净环境启动，完成创建/打开、操作、验证、导出、重开；同一套关键后置条件检查 Studio、SDK、MCP。
4. **补失败旅程。** 以缺少目标、歧义、阻挡、取消和损坏包为最小集合，核验原世界保护、停止条件与用户反馈。
5. **完成外部验收。** 独立首次使用、候选提交托管 CI 和目标硬件测量分别记录。先处理实际阻断，再决定 beta 发布。
6. **进入意图生成。** 对照现有 World IR、Planner、RuleRuntime、Acceptance 实现列差距，只实施支持标准场景所必需的部分。

在任务库中先复核已有条目并复用原 ID；确实缺失的工作才新增到主要所有者的 tasks.jsonl。建议每轮选取 5–10 条直接服务当前里程碑的任务，并限制同时进行的跨域交付；未入选的 READY 不代表本轮实施指令。本文件不建立第二份任务状态表。

## 8. 暂不优先投入

- 持续增加尚未完成碰撞、导航和任务验收的大型展示世界。
- 与当前用户闭环没有直接关联的界面重做、风格包扩张和新入口。
- 为扩大架构而新增执行链、平行状态、目录重构或服务拆分。
- 在小世界创建闭环未成立前同时接入大量生成 Provider。
- 没有基准压力支持的大世界流式化、复杂多人协同或物理后端扩张。

上述能力可以继续保留和研究；进入实施队列时必须说明解决哪个当前验收问题。

## 9. 如何判断进展

按明确测试集报告：首次独立使用到首次 verified 交互的时间；世界创建满足率；任务真实成功率；错误宣称成功次数；取消后的违规继续次数；干净环境重开后的任务成功率；目标硬件的加载时间、帧时间和资源释放。

建议零容忍目标是“错误宣称成功”和“取消后违规继续”；约五分钟首次交互沿用已有首次使用目标。其他阈值在测量基线后设定，本次不编造成绩和性能承诺。
